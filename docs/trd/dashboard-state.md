# Dashboard state ownership

The dashboard edits core settings, chat records, character footers, host
services, and device appearance from one shell. Each row below names the
field, where its truth lives, who may change it, how the write is ordered
and audited, when it applies, what blocks it, and the nearest test path.
Scope, activation, audit, and recovery for registered settings follow
[the setting keys](data.md#setting-keys). Route parity lives in
[route parity](dashboard-routes.md). The visual contract is
[the AIRA web design contract](../DESIGN.md).

## How to read this page

- **Authority** is the store or service that decides the value.
- **Writer, revision, audit** names the route or function, the concurrency
  check, and the `setting_change` record.
- **Tests** cites the nearest suite from [traceability](traceability.md).
  **Passing** means the suite is cited there for the requirement.
  **Unverified** means the code path was read for this change but no
  field-level test was confirmed here. **Planned** means
  [site](site.md) marks it not built.

## Chat, type, and global settings

Every registered key resolves through global, then chat type, then chat
instance. The nearest level with a value wins. Reads come from
`GET /api/chats` (resolved values with source level and `settingsRevision`)
and `GET /api/settings?level=&scope=` (raw rows at one level). Writes go one
key at a time through `PUT /api/settings` with `{ level, scope, key, value }`.
`value: null` clears the row and restores inheritance. An optional
`expectedRevision` is compared inside the write transaction; a mismatch
returns 409 `stale_revision` and the draft is kept for comparison. Every
applied change writes one `setting_change` row with actor `site`.
Implementation: `src/settings/settings.ts`, `src/settings/keys.ts`,
`src/api/routes.ts`, `src/api/writes.ts`.

## Persona

Character Studio reads repository and data packs. A repository pack can be copied into a new data pack.
The protected core writer validates and publishes data packs. The simulator consumes a local draft.

## Deployment configuration

`config.yml` is validated at start-up against `src/config/schema.ts`. An
unknown key or wrong type stops start-up. The dashboard shows sanitized
effective and applied revisions. Secrets stay on the host in `.env` and are
never printed or committed.

## Host settings, routines, notices, markets, and files

These pages reach the host owner service through the core's same-origin
`/owner-api/` prefix. Owner credentials travel only in the protected header.
The core strips the prefix, forwards, and propagates refusal or service
failure. Core paths such as `/api/chats` keep their own shapes. See
[site](site.md#owner-page-edits).

## Remaining installed checks

Exercise the protected routes on the installed build, including the owner credential, real host revisions,
rollback to the prior entry and preservation of writes since the switch. Keep private values out of the
release record. See [deployment](deployment.md) and [traceability](traceability.md).
