# Dashboard state ownership

The dashboard edits core settings, chat records, character footers, host
services, and device appearance from one shell. Each row below names the
field, where its truth lives, who may change it, how the write is ordered
and audited, when it applies, what blocks it, and the nearest test path.
Scope, activation, audit, and recovery for registered settings follow
[the setting keys](data.md#setting-keys). Route parity lives in
[route parity](dashboard-routes.md). The visual contract is
[the AIRA web design contract](../DESIGN.md).

## How to read this page

- **Authority** is the store or service that decides the value.
- **Writer, revision, audit** names the route or function, the concurrency
  check, and the `setting_change` record.
- **Tests** cites the nearest suite from [traceability](traceability.md).
  **Passing** means the suite is cited there for the requirement.
  **Unverified** means the code path was read for this change but no
  field-level test was confirmed here. **Planned** means
  [site](site.md) marks it not built.

## Chat, type, and global settings

Every registered key resolves through global, then chat type, then chat
instance. The nearest level with a value wins. The dashboard reads resolved
values and `settingsRevision` from `GET /owner-api/core/chats` and raw scoped
rows from `GET /owner-api/core/settings?level=&scope=`. Each `PUT /owner-api/core/settings`
sends `{ level, scope, key, value, expectedRevision }`. A null value clears
the row and restores inheritance. The write compares the revision inside the
transaction. A stale revision returns 409 and keeps the draft available for
comparison. An applied change writes a `setting_change` row with actor `site`.

The [Chromium field matrix](../../tests/browser/chat-settings-fields.browser.ts)
checks representative changes, visible source and inheritance, and sender
admission before and after clearing an override. Rows distinguish control
checks from writes.
Two-session conflicts and editable character binding are covered by the
[browser state suite](../../tests/browser/dashboard-state.browser.ts).

## Deployment configuration

`config.yml` is validated at start-up against `src/config/schema.ts`. An
unknown key or wrong type stops start-up. The owner dashboard shows only
opaque revision tokens for the startup-applied and currently valid file
revisions, plus status and timestamps. Secrets stay on the host in `.env` and
are never printed or committed. No dashboard writer edits deployment files.

`GET /owner-api/core/config` is the exact readback endpoint. It requires the
existing protected owner credential, `Host` and `Origin` checks, and answers
with `no-store` and a generated `X-Request-Id`. It returns only
`{ appliedRevision, currentRevision, status, checkedAt, appliedAt }`, where
each revision is the SHA-256 hex of the canonicalized parsed config
(post-normalization, as parsed at start-up), or `null` when there is no valid
revision to report. No config value, secret or path is returned. Any non-`GET`
method gets `405`. The same path without the protected prefix is not a public
route and gets `404`. Access without the owner credential gets `401`.

### Deployment activation readback

- **Startup-applied revision.** `appliedRevision` is captured from exactly the
  `Config` object parsed at start-up, including normalization (ignored-key
  stripping), as `revisionForConfig` in `src/config/status.ts`. It never
  changes for the life of the process.
- **Currently valid file revision.** Every `GET` rereads the same authoritative
  config path the process started from (`AIRA_CONFIG` or `config.yml`) with a
  fresh file descriptor, verifies that the inode is still linked, then parses
  it with the same `parseConfig` and hashes it the same way. A valid file
  yields `currentRevision`; anything else yields `null`.
- **Missing or malformed file fault.** An unreadable source (missing file,
  permission denial, read error, or an unlinked single-file bind mount) reports `status: "inaccessible"`. Unparseable
  YAML or a schema failure reports `status: "invalid"`. Both keep
  `appliedRevision` intact, return `200`, and never expose the file error text,
  path or contents: the fault is named only by its status. A malformed file
  never changes what the running process applies.
  Recreate the container after an atomic host replacement of a single-file bind mount.
- **Restart semantics.** `status: "current"` means the file still parses to the
  applied revision. `status: "pending_restart"` means the file parses to a
  different valid revision that applies only after a restart. Restarting on a
  valid edit adopts it as the new `appliedRevision`. Restarting on an invalid
  file fails start-up as before, so the invalid edit is never adopted.
- **In-memory config.** When the running config was injected without a source
  file (tests, harness), there is no path to reread. The endpoint reports
  `status: "memory_only"` with `currentRevision: null` and the in-memory
  applied revision, labelling that the file state cannot be checked.
- **Health UI.** The System Health page reads this endpoint on load and refocus
  and renders one of: running revision (`current`), pending restart
  (`pending_restart` with both tokens), invalid file (`invalid`, applied intact)
  or inaccessible source (`inaccessible`, applied intact). It shows only the
  opaque tokens and timestamps.

### Running core settings

`GET /owner-api/core/deployment-settings` requires owner authentication and returns a read-only view
of the startup-applied configuration. Models identifies the main transport (Claude Code subscription,
Anthropic API, or OpenAI-compatible API), the API fallback, normal and /think effort, and route availability.
Core Configuration covers every schema group. Private paths, commands, identifiers, and free-text fields
report presence or counts. Model endpoints expose only the HTTP(S) origin. Credentials reports presence
for named core integrations, never their values. The host settings CLI owns the installed config and secret files. Authenticated reads return field types,
safe display values, credential presence and an opaque revision. Edits require this revision, validate the
complete candidate against the core schema, and preserve untouched fields. Secrets travel only in POST bodies.
Applying saved edits recreates the current image under the deploy lock. A failed health check restores the
previous files and image. The UI shows pending edits and distinguishes saved values from the running core.
`/owner-api/core/config` retains its revision-only contract. Host-owned integrations keep their existing writers.

## Host settings, routines, notices, markets, and files

These pages reach the host owner service through the core's same-origin
`/owner-api/` prefix. Owner credentials travel only in the protected header.
The core strips the prefix, forwards, and propagates refusal or service
failure. Core paths such as `/api/chats` keep their own shapes. See
[site](site.md#owner-page-edits).

## Remaining installed checks

Exercise the protected routes on the installed build, including the owner credential, real host revisions,
rollback to the prior entry and preservation of writes since the switch. Keep private values out of the
release record. See [deployment](deployment.md) and [traceability](traceability.md).
